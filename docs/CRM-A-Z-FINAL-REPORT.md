**This section is not legal advice and this project makes no claim of legal compliance.** These items

## 16. Webhook processing latency — BLOCKER before live WhatsApp or Lead Ads activation

### Measured, not assumed

| Fact | Value | Source |
|------|-------|--------|
| System cron schedule | **`3-59/15 * * * *` — every 15 minutes** | `crontab -l` (a provider "cron frequency monitor" rewrote a plain `*/15` to a stable 3-minute offset; the interval is unchanged) |
| Cron target | `/home/hyundaic/bin/crm-cron.sh` → `https://crm.roozbeh.com.tr/cron/index/<key>` | wrapper script |
| Perfex cron throttle | **300 s (5 min)** — `hooks()->apply_filters('cron_functions_execute_seconds', 300)` | `application/controllers/Cron.php:18` |
| Throttle behaviour | Runs only if `time() > last_cron_run + 300`. Because invocations are 900 s apart, **the throttle never blocks a run and never adds delay** | `Cron.php:20` |
| **Effective worst-case processing latency** | **≈ 15 minutes** (plus processing time) — **not 5 minutes** | derived from the two facts above |

**Correction:** any earlier statement implying ~5-minute webhook processing was wrong. The 300 s throttle is
a *floor* on how often the cron body may execute, not the schedule. The schedule is 15 minutes, so 15 minutes
is the ceiling on how long a received webhook waits before it is processed.

Every asynchronous consumer hangs off the single `after_cron_run` hook, so all of them inherit that 15-minute
ceiling: `se_wa_process_pending`, `se_wa_consume_due_reminders`, `se_outbox_drain`, `se_leadgen_process_pending`,
`se_leadgen_reconcile`, `se_gdm_poll_pending`, `se_report_import_all`.

### The receive path is already correct — do not change it
`modules/se_whatsapp/controllers/Webhook.php` verifies `X-Hub-Signature-256` over the raw body with
`hash_equals`, stores the event deduplicated on a SHA-256 of the raw body, and returns `200` immediately.
No Meta or Google call happens inline with the request. The latency is entirely the drain interval.
**This property must be preserved by any change below: the endpoint verifies, enqueues, and returns
quickly, and must never perform slow Meta/Google work inline.**

### Status
**Cron was NOT changed in this phase.** This is recorded as a blocker to be resolved *before* live WhatsApp
or Lead Ads activation, not after.

### Two cPanel-compatible options

**Option 1 — tighten the existing cron to every five minutes.**
Change `3-59/15 * * * *` to `3-59/5 * * * *` (or `*/5`) **only after** measuring that a complete run finishes
well inside five minutes. Also raise the Perfex throttle to match, otherwise the extra invocations are
discarded by the 300 s gate and nothing improves:

```php
// application/config/hooks.php or a small module hook
hooks()->add_filter('cron_functions_execute_seconds', function () { return 60; });
```

*Trade-off:* the heavy Perfex core cron (mail queue, recurring invoices, reminders, plus all seven module
consumers) then runs 3× more often on shared hosting. Measure first: time ten consecutive runs and require
the 95th percentile to be under ~120 s before adopting this.

**Option 2 — PREFERRED: a separate lightweight webhook-event processor every one minute.**
Leave the heavy Perfex cron at 15 minutes and add a second cPanel cron entry, `* * * * *`, hitting a
*narrow* endpoint that drains only the latency-sensitive queues:

- `se_wa_process_pending()` — WhatsApp webhook events
- `se_leadgen_process_pending()` — Lead Ads events
- `se_outbox_drain()` — conversion outbox (optional here; conversions are not latency-critical)

Requirements for that endpoint: its own key (not `APP_CRON_KEY`), a short bounded batch, an overlap guard
(a lock option or the existing lease mechanism), no core Perfex cron tasks, and a hard time cap so a slow run
cannot pile up. This gives **≈ 1-minute** worst-case webhook latency while the heavy cron keeps its 15-minute
cadence and its current resource profile.

*cPanel note:* cPanel supports one-minute cron entries, but some shared hosts enforce a minimum interval or a
concurrent-process cap. Confirm with the host before adopting; if one minute is refused, five minutes on the
narrow endpoint still beats fifteen.

**No cron entry, hook or endpoint was created in this phase.**

**Finding 17.1 — every ad-platform secret is designed to be stored as plaintext in `tbloptions`.**
There is **no encryption anywhere in the custom modules**: a source-wide search for `openssl_*`, `sodium_*`,
`encrypt`, `decrypt`, `getenv`, `$_ENV` and CI's Encryption library returns **zero** matches. Anything with
read access to the database — a dump, a backup file, a SQL-injection foothold, a support engineer — reads
every token in the clear.

**Finding 17.2 — no secret is currently populated, so there is no live exposure today.**
The options table holds only **7** `se_*` rows: `se_core_schema_version`, `se_appt_schema_version`,
`se_meta_last_reconcile_at`, and four duplicate `se_wa_rates_json` rows. **None of the credential option
names above exists in the database yet.** The exposure is a design defect awaiting first use, not a live
leak. *(Minor, unrelated: `se_wa_rates_json` is duplicated four times and should be de-duplicated.)*

**Finding 17.3 — Google authentication is designed around a manually stored static bearer token.**
`se_gdm_access_token()` (`modules/se_core/se_google_dm.php:39-42`) returns the raw option value and
`se_gdm_ingest()` sends it as `Authorization: Bearer <token>`. There is no service-account key, no JWT
assertion, no OAuth token exchange, and no refresh path. **Google service-account access tokens expire in
about one hour**, so this design breaks roughly hourly and requires a human to paste a new token. It is not
viable for a live integration.

**Required design — target state**

- A secret must **never be displayed again after saving** (write-only field; show a "configured / not
  configured" indicator only, which is what the health endpoints already do).
- Prefer a **cPanel environment / config-file reference** (a constant in `app-config.php`, mode `600`,
  gitignored) or **encrypted ciphertext at rest**.
- If encrypted in the database, the **encryption key must live outside the database and outside Git** —
  in `app-config.php` or the environment, never in a table that a DB dump captures.
- **Configuration files restricted to owner-only permissions.** *Verified today:*
  `application/config/app-config.php` and `application/config/database.php` are both **mode `600`,
  owner `hyundaic:hyundaic`** — correct.
- **Logs and health endpoints must never expose secret values.** *Verified today:* `se_meta_health()`,
  `se_google_health()` and `se_integration_health()` expose only booleans (`token_configured`,
  `sa_token_configured`, `externally_gated`); `se_outbox_process_row()` truncates and redacts errors and
  never writes a payload or token; `se_wa_app_secret()` is documented as never logged. **No secret is
  exposed by any health surface or log path** — this part of the design is already correct.

**Required design — Google Data Manager specifically**

- **Do not** build live authentication around a manually stored bearer token such as
  `se_google_sa_token_<brand>`.
- Use **service-account credentials** (JSON key → signed JWT → token exchange) or **Application Default
  Credentials** to obtain **renewable short-lived access tokens**, cached until shortly before expiry.
- Store only the **secure credential reference / configuration needed for renewal** — a filesystem path to

## 18. Conversion attribution snapshot — CORRECTNESS DEFECT

**Question:** does each conversion outbox row snapshot the attribution and consent state that existed
**when the conversion event occurred**?

**Answer: no.** Both senders rebuild the conversion from the lead's **current, mutable** row at send time.

### What is verified correct

| Property | Verdict | Evidence |
|----------|---------|----------|
| First-touch attribution is immutable | **Correct** | `se_attr_first_touch_fields()` writes `gclid/gbraid/wbraid/fbclid/fbc/fbp/ctwa_clid/utm_*/landing_url/referrer/first_touch_at` to primary lead columns; the browser store only sets `s.first[k]` when unset (`se_attribution.php:111`), and the persist hook runs once on `web_to_lead_form_submitted`. |
| Last-touch may update on later interactions | **Correct, and structurally separated** | Parallel `last_*` columns via `se_attr_last_touch_map()`; the latest click never overwrites the original. |
| Event ID stable across retries | **Correct** | Meta `event_id = 'se-' . lead_id . '-' . row_id`; Google `transactionId = 'se-gdm-' . lead_id . '-' . row_id`. Both derive from immutable primary keys, so a retry re-sends the same id and the platform de-duplicates. |
| Event time / event name stable | **Correct** | Both are snapshotted onto the outbox row at queue time and read from the row, not recomputed. |
| Queued conversions inherit a later **last-touch** value | **Not currently happening** | `se_gdm_build_event()` reads `$lead->gclid/gbraid/wbraid` — the *first-touch* columns. The `last_*` columns are never consulted by any sender. The separation of last-touch into its own columns is what prevents the bleed. |

### The defect

`se_capi_send_event()` (`se_capi.php:58-59`) and `se_google_dm_send_event()` (`se_google_dm.php:158-159`)
both execute `SELECT * FROM tblleads WHERE id = <lead_id>` **at drain time** and hand that live row to the
pure builders. The outbox row carries only `brand_id`, `lead_id`, `destination`, `event_name`, `event_time`,
`dedup_key` and retry metadata.

`tblse_conversion_outbox` **has a `payload` column**, and `se_outbox_queue()` accepts a `$payload` argument —
but every caller passes the default `[]`, so it is always stored as `[]`, and **no sender ever reads it**.
Confirmed in the database: `0` of `0` outbox rows carry a non-empty payload. The snapshot mechanism was
scaffolded and never wired up.

**Consequences**, for any row that sits pending between queue time and drain time (up to 15 minutes
normally, and far longer whenever the outbox is gated, held, or retrying — which is the *current* state,
since every destination is externally gated and rows hold as `pending`):

1. **Consent is not snapshotted.** `se_outbox_on_status_change()` checks `consent_ads` at *queue* time, but
   `se_gdm_build_event()` re-reads `$lead->consent_ads` at *send* time and stamps
   `CONSENT_GRANTED`/`CONSENT_DENIED` from the **current** value. A consent withdrawn after queueing changes
   what is transmitted for a historical event, and a consent *granted* later would transmit a conversion that
   had no consent when it happened. The Meta sender does not re-check consent at send time at all.
2. **`consent_text_version` is never captured on the row.** The append-only `tblse_consent_ledger` does hold
   the version and timestamp, so the state *is* historically reproducible in principle — but no sender and no
   helper reconstructs it. `se_consent_current()` returns only the **latest** state; there is no
   "state as at timestamp T" lookup.
3. **Identifiers are rebuilt live.** `email`, `phonenumber` and `meta_lead_id` are ordinary mutable lead
   fields. A correction, merge, or erasure between queue and send silently changes the identifiers attached
   to a historical conversion.
4. **Source attribution is derived live.** Google's `eventSource` is computed as
   `!empty($lead->ctwa_clid) ? 'MESSAGE' : 'WEB'` at send time. In practice `ctwa_clid` is a first-touch
   immutable column so this is stable today — but it is stable by accident, not by design.

A related, smaller issue: `se_landing_apply_to_lead()` (`se_google_dm.php:308-326`) writes `gclid/gbraid/wbraid`
onto a lead **unconditionally**, with no "only if empty" guard, so a second landing token can overwrite a
first-touch click id. Guard it with the same first-touch rule the rest of the system uses.

### Proposed remediation — additive, idempotent, NOT applied

Documented here as required; **nothing was migrated or applied in this phase.**

1. **Schema (additive only, `se_core` schema v8).** No column is dropped or rewritten:
   ```sql
   ALTER TABLE `tblse_conversion_outbox`
     ADD COLUMN IF NOT EXISTS `attribution_snapshot` MEDIUMTEXT DEFAULT NULL,
     ADD COLUMN IF NOT EXISTS `consent_snapshot`     TEXT       DEFAULT NULL,
     ADD COLUMN IF NOT EXISTS `snapshot_version`     TINYINT NOT NULL DEFAULT 0;
   ```
   Guarded by `IF NOT EXISTS` and the existing `se_core_schema_version` gate, so re-running is a no-op.
2. **Producer.** `se_outbox_queue()` captures, at queue time: the first-touch click ids and UTMs, `fbc`,
   `fbp`, `ctwa_clid`, `meta_lead_id`, the **already-hashed** e-mail and phone (never plaintext), and the
   consent state plus `consent_text_version` plus the consent-ledger row id in force at `event_time`. Sets
   `snapshot_version = 1`.
3. **Senders.** `se_capi_build_event()` and `se_gdm_build_event()` read the snapshot when
   `snapshot_version >= 1`, and fall back to the live lead row when it is `0`. That fallback is what makes
   the migration safe for rows queued before the change — **no backfill, no rewrite of existing rows**.
4. **Idempotency.** Re-running the migration, re-queuing the same stage on the same day (the `dedup_key`
   already prevents duplicates), and retrying a claimed row all remain no-ops. `event_id` / `transactionId`
   are unchanged, so platform-side de-duplication is unaffected.
5. **Also fix** `se_landing_apply_to_lead()` to write a click id only when the column is empty.

**Status: live conversion sending is BLOCKED on this finding until the remediation is reviewed and applied.**
