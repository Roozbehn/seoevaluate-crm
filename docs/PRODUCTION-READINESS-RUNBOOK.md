## 7.1a Asynchronous processing latency (blocker before live WhatsApp / Lead Ads)

Every async consumer hangs off the single `after_cron_run` hook — `se_wa_process_pending`,
`se_wa_consume_due_reminders`, `se_outbox_drain`, `se_leadgen_process_pending`, `se_leadgen_reconcile`,
`se_gdm_poll_pending`, `se_report_import_all` — so all of them inherit the 15-minute cron interval.

The WhatsApp webhook receiver is already correct and **must stay that way**: it verifies
`X-Hub-Signature-256` over the raw body, stores the event deduplicated, and returns `200` immediately, with
**no Meta or Google call inline**. The latency is entirely the drain interval, not the request path.

**Option 1 — tighten the existing cron to five minutes.** Change `3-59/15` to `3-59/5` *and* raise the
throttle, or the extra invocations are simply discarded by the 300 s gate:
```php
hooks()->add_filter('cron_functions_execute_seconds', function () { return 60; });
```
Only after measuring that a complete run finishes well inside five minutes (time ten consecutive runs;
require p95 < ~120 s). Trade-off: the heavy Perfex core cron then runs 3× more often on shared hosting.

**Option 2 — PREFERRED: a separate one-minute webhook-event processor.** Leave the Perfex cron at 15
minutes; add a second cPanel entry `* * * * *` hitting a narrow endpoint that drains only
`se_wa_process_pending()` and `se_leadgen_process_pending()`, with its own key (not `APP_CRON_KEY`), a
bounded batch, an overlap guard, a hard time cap, and no core Perfex tasks. Gives ≈ 1-minute worst-case
webhook latency. Confirm the host permits one-minute cron entries; if not, five minutes on the narrow
endpoint still beats fifteen.

**Neither option was applied. Cron was not changed.**

## 7.2 Deployment & rollback runbook

### Preflight (all must pass)
1. `cd /home/<prod_user>/<docroot> && git status` clean; on the intended release commit.
2. Confirm PHP/MariaDB versions and the extension set above.
3. Take backups (see BACKUP-RESTORE-RUNBOOK) — DB + `application/config/app-config.php` + `modules/`.
4. Confirm `application/config/app-config.php` (mode `600`, untracked) has the DB creds, `APP_BASE_URL`, a
   fresh `APP_CRON_KEY` and `APP_CSRF_PROTECTION=true`.
   **Secret-storage warning:** ad-platform secrets are currently designed to be stored as **plaintext rows
   in `tbloptions`** — there is no encryption anywhere in the custom modules. Read
   `docs/CRM-A-Z-FINAL-REPORT.md` §17 before storing any live token; a secret must never be redisplayed
   after saving, and any encryption key must live outside the database and outside Git.

### Maintenance window
- Optional for a code-only deploy (idempotent migrations). Recommended for the first cutover.

### Code deployment (explicit paths)
1. `git fetch origin && git checkout main && git pull --ff-only origin main`
2. Verify `git rev-parse HEAD` equals the reviewed release hash.

### Environment-specific configuration
- `app-config.php` is environment-specific and **untracked** — never overwritten from git.
- **Do not treat `tbloptions` as a safe secret store.** Options are plaintext and are captured verbatim by
  every database dump. Prefer a `600` config-file constant or encrypted ciphertext whose key lives outside
  the database and outside Git (final report §17).
- **Google Data Manager:** do not paste a bearer token into `se_google_sa_token_<brand>` — Google access
  tokens expire hourly. Use service-account credentials or Application Default Credentials to mint
  renewable short-lived tokens and store only the credential reference needed for renewal.

### Database migration order
- Migrations are **idempotent** (`IF NOT EXISTS` + version-gated). They run automatically on the first
  authenticated `admin_init` after deploy. Order is enforced by module load: se_core (v7) → se_appointments (v2).
- To force-apply headlessly: authenticate once in the admin UI (any staff), or run the cron once after login.

### Module activation order
1. se_core → 2. se_appointments → 3. se_whatsapp → 4. perfex_dark_theme (cosmetic, last).
Activation is idempotent; re-activation is safe; no module has a destructive uninstall.

### Cron installation
- The system cron `3-59/15 * * * * /home/hyundaic/bin/crm-cron.sh` calls the wrapper, which reads
  `APP_CRON_KEY` from config at runtime (never in the crontab). Verify one run returns HTTP 200, not 401.
- **Latency:** this schedule gives ≈ 15-minute worst-case async processing. See §7.1a before enabling live
  WhatsApp or Lead Ads.

### Cache / restart
- CloudLinux/LiteSpeed: `touch ~/.lsphp_restart.txt` to clear opcache after a deploy.

### Health verification (post-deploy)
- Login page HTTP 200; one authenticated admin page 200; `/admin/se_core/se_reports/health` renders;
  cron run 200; application error log unchanged; outbox drains without external transmission when gated.

### Rollback triggers
- Login 5xx; migration error; fatal in app log; cron 500; outbox mass-fail; health page error.

### Code rollback
- `git checkout <previous_release_hash>` then `touch ~/.lsphp_restart.txt`. (No history rewrite.)

### Database rollback
- Restore the pre-deploy DB dump into the SAME database only if a schema change caused failure (see
  BACKUP-RESTORE-RUNBOOK). Migrations are additive (`IF NOT EXISTS`); a code rollback rarely needs a DB rollback.

### External-integration rollback
- Set the per-brand toggles off: `se_capi_enabled_<brand>=0`; clear `se_meta_page_token_*`,
  `se_google_sa_token_*`, `se_wa_app_secret`, `se_meta_app_secret` to re-gate all outbound. Nothing sends
  without those; rows hold as pending.

### Final acceptance criteria
- App 200; cron 200; **database schema** applied (se_core v7, se_appointments v2 — module versions remain
  1.0.0); health page renders; **no `error_log*` file inside the document root**; no synthetic data; no
  secrets in git; backup **dump integrity** verified.
- **Backup caveat:** "backups verified" here means *dump completion marker + expected table count + basic
  parse integrity* only. It does **not** mean a restore succeeded or that application recovery is proven.
  An isolated restore test is still outstanding — `docs/BACKUP-RESTORE-RUNBOOK.md`.
