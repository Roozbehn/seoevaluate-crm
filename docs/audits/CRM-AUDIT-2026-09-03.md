## C. UI / UX review — screen by screen

### C.1 Navigation

**[proven]** Sidebar (staff #1): Dashboard · Leads · Patient journeys · Patients · Appointments · WhatsApp · Instagram · Customers · Reports · Integrations (6 children) · Setup. `se_clinic_hidden_sidebar_slugs()` removes sales, subscriptions, expenses, contracts, projects, tasks, support, estimate requests, knowledge base, utilities and Perfex reports at filter priority 1000 (`modules/se_core/se_clinic.php:167-224`), quick-actions are cut to Lead/Customer/Staff, and every SE item is capability-gated (`se_navigation.php:19-21, 119-123`). Seeded roles *Clinic Owner* and *Sales* exist (`se_clinic.php:443-479`); Sales cannot see health answers or photos.

This is good work and the flat order matches the workday. It stops one click in: **Leads** and **Customers** are stock Perfex — the lead modal shows Position, Website, Company, Lead value, Zip, tabs *Proposals / Tasks / Attachments / Reminders*, and a primary blue **Convert to customer** button; the status bar is 14 English stages (`New … WhatsApp Engaged … Deposit Paid … Travel Booked … Treated … Reviewed`, `se_core/pipeline.php:20-32`) even though the clinic takes no deposit and the journey has no state that maps to `Deposit Paid`/`Travel Booked` (`leadsync.php:134-152`). Four nouns describe one person: Lead, Customer, Hasta (a KVKK envelope with no name), Yolculuk (the real record).

**Verdict:** the sidebar reads *purpose-built clinic CRM*; the Leads/Customers screens and the header still read *Perfex with modules*.

### C.2 Dashboard (`se_core/se_dashboard`)

**[proven]** 12 stat cards: Leads (all-time total), Patients, Appointments today, Upcoming appointments, No-show (all-time), Unread, Conversions pending/failed, Meta queue pending, Google submitted, Integration Credentials, Consent Settings. Plus a persistent warning banner. Load: TTFB 735 ms first hit (Cloudflare challenge), 250–360 ms after; DOMContentLoaded 1.5 s; 20 scripts / 822 KB; zero console errors.

| Question the owner asked | Answered on the Dashboard? |
|---|---|
| How many new leads arrived (today)? | No — all-time total |
| Which patients need action today? | **No** (it is on *Patient journeys → Attention items*) |
| Unanswered WhatsApp? | Yes (Unread) |
| Incomplete forms / photos submitted / waiting for review / quotes awaiting decision | No — all on the journey index; quotes *awaiting the patient* are not counted anywhere (`health.php:135` lumps `quote_sent` into "Consultation due") |
| Consultations / procedures upcoming | Appointments (no type split) |
| Post-op follow-ups due | No (journey index) |
| Integrations failing? | Partially — pending/failed outbox only; `skipped` invisible |
| Records stuck? | **No** — no age/staleness anywhere |

**[proven]** The banner "No approved consent text is configured" is a false positive: `se_outbox_ui.php:250` calls `se_consent_text_configured(0)` (global default) while the Consent Settings page shows brand 22 with *Advertising / Marketing / Health data — Ready*. Staff learn to ignore a warning bar, which is the worst outcome for the real warnings that share it.

**Recommendation:** make the *journey index* the landing page for clinic roles (or merge its counters + Attention items into the dashboard), replace all-time counters with *today / this week*, add a "no movement for N days" list, split "Consultation due" into *Quote awaiting patient* vs *Consultation to schedule*, fix the brand-0 check.

### C.3 Leads / Patients / Journeys lists

- **Leads** **[proven]**: 13 columns (`#, Name, Company, Email, Phone, Value, Tags, Assigned, Status, Source, Last Contact, Created`), server-side DataTable (`leads/table` 367 ms). Journey state exists only as a custom field inside the profile, not as a column. Source mismatch observed: lead says *Meta Lead Ads*, its journey says *Organic WhatsApp* — two source vocabularies (`tblleads.source` vs `se_journeys.source`).
- **Patients** **[proven]**: `#, Brand (22), Preferred language, Nationality, State (active)`, no name, no phone, no journey state; search hits only nationality/language (`se_patients.php:233-237`); numbered-button pagination. Staff cannot find a patient by name here. The record is a KVKK envelope (language, nationality, encrypted passport) — valuable, but it should not be labelled *Patients* if it cannot show a patient.
- **Patient journeys** **[proven]**: 10 counter cards, *Attention items*, table `#, Patient, State, Source, Automation, Updated`; capped at 100 rows (`Se_journey.php:30`); no search, no assignee filter, no sort. Patient names fall back to the WhatsApp profile name — one row is literally an emoji.
- Phone rendering: lead `+90…`, inbox raw `905…`, journey `••••3419` — three formats for one number.

**Duplicate handling** (well designed, one gap): `se_journey_normalize_wa_id()` (`helpers.php:758-767`), DB unique `(brand_id, wa_user_id)`, lead reuse by normalised phone over the newest 2 000 leads (`helpers.php:1143-1160`), relink on lead deletion (`:1051-1084`). Gap: website leads dedup only on `website_lead_id`, Lead Ads only on `meta_lead_id` — the same person via WhatsApp then the website becomes two leads **[inferred]**.

### C.4 Patient profile (journey view)

**[proven]** Header: state + timestamp, assignee, next action, source, automation, last automated message, consent badges, first→latest contact; 8-step stepper; action row; tabs *Timeline · Intake · Photos · Review/Quote · Consultation·Procedure·Aftercare*. Everything the brief asks for exists **except**: patient identity block (phone/e-mail/age are on the Lead), free-text notes/call log outside the review form, documents, the WhatsApp composer (reply = leave the page), and translated labels. Timeline entries render as `quote_pending_staff_approval → quote_sent`, `wa_outbound consultation_information (inwindow)`, `staff #1`; consent badges as `health / marketing / publication`; care-tab selects as raw `scheduled/held/…` and `none/requested/…` (`view.php:44-46, 163, 181, 306, 329, 366`).

**Page map for one patient** **[proven]**: Journey ↔ WhatsApp thread ↔ Lead modal; Hasta only from the Patients list (no link from journey or lead); Appointment detail only from the Appointments list. Three pages for a normal question, five if the KVKK record or an appointment matters.

### C.5 Lead → patient journey (current vs target)

See §D. Current path for one organic enquiry to aftercare ≈ 45–55 staff clicks over three page types; the journey page absorbs most of it, which is the right shape.

### C.6 WhatsApp

**Inbox** **[proven]**: `Contact (raw digits), Brand, Related lead (#id), Assigned staff, Unread, Window, Last inbound, View`; filters All / Assigned to me / Unassigned; no search, no message preview, no journey state, no pagination (`Se_whatsapp_model.php:15-25` loads every conversation).

**Thread** **[proven]**: bubbles with delivery state and Meta failure reason, day separators, media, composer (auto-grow, Enter to send, 4 096 counter, emoji, attachment, voice note — all 44 px on mobile), server-decided window badge "Reply window open · open until …", template mode when closed, right panel with conversation facts, **Patient journey** panel (state + *Open journey* + *Start evaluation*), assignment, outbound queue tracker. The tracker copy is hard-coded English ("Replies are queued here and sent by the dispatcher, which runs every minute — next run 23:00:40…", `se_outbound_tracker.php:130-217`). The thread is a fixed 560 px box (`pwa.css`), the page is 2 631 px tall on a laptop, and on load the whole page scrolls ~490 px to reach the newest message, hiding the header.

**Contextual actions:** the thread offers *Open journey* and *Start evaluation* only. The requested set (Send evaluation form, Request photos, Mark photos received, Request review, Prepare/Send quote, Schedule consultation/procedure, Send pre-op, Send aftercare, Schedule follow-up) all exist — on the journey page, spread over four tabs.

**Trap** **[proven in code]**: any composer reply calls `se_journey_note_staff_reply` → `automation_state = paused_staff` (`se_whatsapp/outbound.php:423-424` → `se_journey/helpers.php:1553-1565`). Reminders stop. The thread panel shows *paused by staff* but has no Resume. One live journey is in exactly that state.

### C.7 Appointments

**[proven]** Form: Title, Starts, Ends (native `datetime-local`), Brand, Assigned to, Relation type, Related record, Status, Consultation format, Timezone (IANA list, default Europe/Istanbul), Location, Cancellation reason, Notes. **No appointment-type field** — `appointment_type` exists in schema/model but only the journey's booking form sets it (`se_journey/views/view.php:322`), so a standalone appointment cannot be marked consultation vs procedure, and the list has no type column. Reminder row is hard-wired to "Sending not configured" (`form.php:158`). Conflict refusals surface as the generic "check the date range, brand and relation" although `se_appt_conflict` exists.

**Calendar** **[proven live]**: `se_appointments/se_appointments/index` renders a panel with an empty `#se-appointments-calendar`; the feed route (`se_appointments/feed`) answers 200 with valid JSON, but `typeof $.fn.fullCalendar === 'undefined'` and no calendar script is on the page — `views/calendar.php:27` does `if (typeof $.fn.fullCalendar !== 'function') { return; }` and silently shows nothing. The `admin_url('se_appointments/manage')` links without the controller segment do resolve (Perfex module routing), so the earlier suspicion of a 404 is **not** a defect.

**Reminders** **[proven in code]**: `se_wa_consume_due_reminders` loads the appointment with `where('id', $rem['id'])` — the reminder's id (`se_whatsapp/outbound.php:849`); enqueue never sets `template_ref` (`Se_appointments_model.php:305-315`, `reminders.php:56`) → template `''` → `template_not_approved` → reminder `failed`. Untested (only `se_reminder_enqueue` is covered). The journey's own confirmations and intake/photo reminders are a different path and do work (observed live).

**Same-day consultation → procedure** **[proven]**: state machine allows `consultation_completed → procedure_booked` (`helpers.php:547`); care tab: set consultation *held* + Update (3 clicks), then book type *Procedure* (default 4 h, `consultation.php:60`) (~4 clicks). Works; no one-click "book procedure now" after marking held.

### C.8 Quote

**[proven in code]** `se_journey_quotes`: currency, `amount_min/max` with brand policy *hidden | range | exact* (range is the default — matches the 45–50k TRY practice), scope in / scope out lists, deposit terms, travel notes, validity, recommendation (consultation first / procedure after consultation), internal notes + internal margin never sent; versioning (editing a sent quote → v+1, editing a pending-approval quote → back to draft); approval gate *draft → request approval → approve (capability) → send to patient* enforced in the helper (`review.php:244-247, 311-315`); sent quote frozen as a hashed snapshot with a mandatory disclaimer; patient answer by WhatsApp buttons / keywords / secure page, shown as *accepted / revision requested / no answer yet*; acceptance auto-sends the booking link. This is the best-designed area of the system.

Gaps: `valid_until` stored but nothing expires a quote or reminds; no PDF; deposit fields prominent for a no-deposit clinic; Sales role cannot see the Review/Quote tab at all (`view.php:100`) so a salesperson cannot read the quote they discuss.

## D. Workflow map

### D.1 Current state (as implemented, organic WhatsApp enquiry, staff-started)

```
Patient writes on WhatsApp
  └─ auto: lead found/created by normalised phone, journey created, welcome with buttons (ad/IG/website sources, or organic if flag on)   [helpers.php:1608-1789]
Staff (thread) ── "Start evaluation" (only if organic auto-start is off)
  └─ auto: privacy notice → Flow "Fill the form" → autosave → submit → photo request → partial acks → 3 photos → ready_for_review → task "Intake submitted — review…" (due +2 d)
Staff (journey › Photos)   classify ×3 → Accept photos → Ready for review          ← MANUAL, 8–10 clicks
Staff (journey › Review)   notes + decision → Save review                          ← MANUAL
Staff (journey › Quote)    amounts/scope → Save draft → Request approval
Owner (journey › Quote)    Approve quote → Send to patient                          ← MANUAL, approval gate (good)
  └─ auto: quote message + secure page + info links; accept → booking Flow/link; revise → ack + task
Patient self-books  └─ auto: appointment + confirmation (.ics); OR staff books (care tab, ~6 clicks)
Staff (care tab)           consultation held + Update                               ← MANUAL (cron only marks held if someone marks the appointment)
Staff (care tab)           book procedure (same day OK) → start pre-op checklist → "Procedure completed"   ← MANUAL, ~7 clicks
Staff (care tab)           Start aftercare plan                                     ← MANUAL (should be automatic)
  └─ auto: protocol steps, check-ins, 48 h no answer → followup_due, urgent-keyword alerts
Staff                      Mark journey completed / Close (lost)
Any staff reply from the composer at any point ⇒ automation paused, no resume in the thread   ← HIDDEN SIDE-EFFECT
```

Manual steps: 9. Duplicate entries: patient identity typed twice when a website lead and a WhatsApp thread are matched late; appointment type re-entered. Automatable: aftercare start, consultation-held from appointment time + confirmation, quote expiry, review SLA nudges, photo auto-classification prompt (patient labels via Flow). Missing states: quote expired, consultation reminded, procedure day (same-day), long-term follow-up (month 3/6/12 as states, not just sends). Unsafe transitions: `quote answer with stale state → forced quote_sent` is a repair path that masks bugs (`helpers.php:1843`); staff reply ⇒ pause without confirmation.

### D.2 Target state

```
Inbound (any channel) ── identity resolved on E.164 phone (one lead per person) ── journey auto-started per source flag
Patient-owned phases (consent, form, photos, quote answer, booking) ── fully automatic with reminders (exists)
Staff-owned phases ── ONE queue: "Needs me today" = review due · quote approval · quote sent >3 d · consultation to schedule · held-not-recorded · procedure done-no aftercare · follow-up unanswered
```

## P. Final decision

### **B — READY WITH FIXES**

The system is already carrying real patients through WhatsApp intake → photos → review → approved quote → self-booking, with audited transitions, sealed health data, correct webhook handling and an unusually large test suite; nothing found corrupts or exposes patient data, and no P0 exists. It is **not** yet trustworthy for four things staff will assume work: appointment reminders (dead path), the calendar (blank), replying from a phone (composer collapses), and ad-conversion feedback (100 % silently skipped behind a green Health page). Those four, the CSRF anchor, and the silent automation pause are the P1 set — all S/M effort, all low-risk, and all shippable in the first two weeks of Phase 1. Until they land, use the CRM on desktop/tablet-landscape for the WhatsApp journey, book consultations through the journey page (its confirmations work), and treat the standalone appointment form's reminder and the calendar as not available.

No production changes were made during this audit. The backlog above and the execution sequence at the end of §N are the proposed order; the first code change should wait for your review of Findings 2 (consent-purpose decision) and 5/6 (host constants), because both need a decision or a host check rather than code alone.
